# 少額で始める分類

## 構成と設定

収集 (`npm run collect`) と有料の分類 (`npm run classify`) を分離しています。モデル設定がなくても文書の全件発見は続きます。未知の名称をキーワードで除外しません。

GitHub Actions Variables に `CLASSIFIER_URL`、Actions Secret に `CLASSIFIER_API_KEY` を設定します。OpenAI の場合 URL は `https://api.openai.com/v1/chat/completions`。キーには Models Read と Chat Completions Write が必要です。

既定は自動選択です。実行のたびに GET /models を取得し、対応表に載っているモデルのうち低価格のものを選びます。既存の `CLASSIFIER_MODEL` や共通単価変数は自動選択時には使いません。現在の候補と予約計算用の単価は次です（USD / 100万トークン）。

| 候補 | 入力 | 出力 |
| --- | --- | --- |
| gpt-4.1-nano | 0.10 | 0.40 |
| gpt-4o-mini | 0.15 | 0.60 |
| gpt-4.1-mini | 0.40 | 1.60 |

これらは GET /models から取得した価格ではなく、予約計算用の初期対応表です。最新料金を実行時に検証する仕組みはありません。提供元の料金変更時は対応表を更新してください。既知モデルの日付付き版にも対応し、未確認モデルや高額モデルへ無条件には切り替えません。推論で HTTP 404 / model_not_found が返った場合だけ、そのモデル系統を今回の実行から除いて次候補へ進みます。失敗分も予約額に残り、全候補で同じ累積上限を使います。401・403・429等は別候補への切り替えをせず停止します。候補がなければ理由を表示して停止します。

必要なら `CLASSIFIER_MODEL_PROFILES` に `[{"id":"モデル名","inputRate":入力単価,"outputRate":出力単価}]` の形式のJSONで対応表を上書きできます。自動選択に使う単価はここでモデルごとに保持するため、別モデルの価格を誤って流用しません。

`CLASSIFIER_MAX_USD` は累積予約額上限。未設定なら0.10です。固定モデルに戻す場合だけ `CLASSIFIER_SELECTION=fixed` と、`CLASSIFIER_MODEL`、`CLASSIFIER_INPUT_USD_PER_MILLION`、`CLASSIFIER_OUTPUT_USD_PER_MILLION` を設定します。固定モードでは単価未設定の有料処理は開始しません。

モデル未設定でも利用可能な候補があれば選択でき、選択したモデル・単価は Actions Summary に表示します。モデルが変わった場合、分類前に少量評価を自動実行します。評価も同じ累積予算内で、合格するまで本分類を行いません。キーはチャットやGitに貼らないでください。

## モデル利用可否を GitHub Actions で調べる

API キーに Models Read 権限を設定した後、「Daily standards discovery」を手動実行して mode=`models` を選択します。設定済みの `CLASSIFIER_URL` と `CLASSIFIER_API_KEY` で `GET /v1/models` を呼び、Summary とログに利用可能なモデル名と `CLASSIFIER_MODEL` の有無を表示します。ローカルPCは不要です。

このモードは推論を呼ばず、カタログ変更・予算予約・更新PR作成も行いません。単価設定も不要です。`listed: false` の場合は一覧を表示した後にジョブを失敗扱いにします。Models Read が不足している場合はHTTP 403等の安全な診断だけ表示します。キーと生レスポンスは表示しません。

モデル一覧にあることと、Chat Completions の利用権限・請求設定・パラメーター互換性は別です。一覧で確認できた後に `evaluate` を実行してください。ローカルで行う場合は `npm run check:models` です。

## 1. 少量評価

「Daily standards discovery」を手動実行し、mode=`evaluate` を選びます。ローカルでは `npm run evaluate`。

GNAP、OAuth、JWT、ACME、RATS、無関係なRFC、未知の用語を使った架空仕様、プロンプト注入を含む12件の人手作成の短い概要で評価します。公式本文の引用ではありません。期待ラベルはモデルに渡しません。

`reports/evaluation/latest.json` に再現率・適合率・判断困難数・実行時間・予約額・返却されたトークン使用量を保存します。モデル未設定時はテストデータの形式だけ検証し、精度は測定していないと表示します。

分類の開始条件は再現率90%以上、適合率80%以上、判断困難0件です。この12件は最低限の回帰チェックで、全48,000件の精度の保証ではありません。特に見落としと紛らわしい仕様を追加して評価セットを育てます。評価データ変更時は fixture version も更新してください。モデル・エンドポイント・プロンプト・評価セットの版が違う過去の合格結果は使えず、分類前に評価を自動実行します。

## 2. 初回分類を再開可能な小分けで実行

評価結果を含む日次PRを確認・マージした後、同じワークフローで mode=`backfill`。通常は最大500件/実行（limit入力で変更、上限5,000）。10文書ずつ1リクエストにまとめ、予約額上限の方が先に尽きれば停止します。上限に収まるよう最後のバッチを小さくできます。

成功したバッチごとにカタログと進捗を保存します。途中のAPI障害でも完了分と費用予約をPRに残し、次の実行は未処理から再開します。日次PRブランチから未マージの結果も引き継ぎます。`reports/classification/` に完了文書、残件数、停止理由があります。

最初から全件完了を狙わず、初回結果の関連文書・除外文書を人が確認し、評価で得た文書当たり費用を参考に次の上限を決めます。精度に問題があればモデルや評価セットを修正します。既存の非関連判定を新モデルで再分類する機能はまだありません。

## 3. 日次処理

定期実行は mode=`daily`。全件発見の後、新規・更新文書を優先して最大30件を分類し、余力で既存の未処理文書を進めます。新規・更新日時を索引の追加要素として保持するので、後日の実行にも優先順位を引き継ぎます。判断困難の再試行には7日の間隔を設けます。

## 費用の扱い

`catalog/classification-budget.json` は評価と分類で共有する累積台帳です。上限は1日ごとのリセットではありません。0.10 USDを使い切ったら、明示的に上限を引き上げるまで有料処理を止めます。台帳を削除して残高をリセットしないでください。

送信JSONのUTF-8バイト数＋オーバーヘッドから入力トークン数を保守的に見積もり、出力上限と設定単価を合わせて**送信前に費用を予約**します。失敗・タイムアウトでも返金扱いにせず、モデルAPIを自動再試行しません。実使用量が少なくても予約は戻しません。小さい予算で予約が収まらない場合、有料呼び出しはゼロ件です。

この上限は設定単価・互換APIの出力上限が正しい前提のローカル予約額です。請求額そのものを保証する仕組みではありません。利用提供元の利用上限も併用してください。使用量を返さないAPIは予約額だけ記録し、実トークン数・実費を測定できたとは扱いません。

ワークフローは同時実行を禁止し、失敗時も台帳・完了分をPRへ保存します。PR保存が失敗した場合の復旧用にActions artifactにも保存します。PR保存やジョブが中断された場合は、再実行前にartifact/台帳の保存を確認してください。ローカルで分類コマンドを並列実行しないでください。

## 評価が失敗した場合

最後の `Report model failure ...` の `exit 1` は、前段の失敗をジョブへ伝える処理です。元の原因は `Evaluate or classify` を確認してください。評価失敗時も `latest.json` を `failed` に更新し、安全なHTTPステータス・エラーコード・パラメーター名を保存します。APIからの生メッセージやキーは保存しません。

| 保存されたエラー | 確認する箇所 |
| --- | --- |
| HTTP 401 | キーの有効性・Secrets登録 |
| HTTP 403 | キーのChat Completions権限・プロジェクトのモデル利用許可 |
| HTTP 404 | モデル名・そのプロジェクトからの利用可否 |
| HTTP 429 + insufficient_quota | APIの課金設定・残高・利用上限。ChatGPT契約とは別 |
| HTTP 429 + rate_limit_exceeded | レート制限。制限解消後に手動再実行 |
| HTTP 400 | `param`やエラーコード、API形式・モデル対応 |
| budget_exhausted | 台帳の累積予約額と明示的な上限 |
| metricsの閾値未達 | 精度評価の誤判定。通信障害とは区別 |

失敗時の予約額は実際の請求額を意味しません。失敗した同一モデルの呼び出しは自動再試行せず、予約も戻しません（自動選択時の model_not_found だけは別候補へ進みます）。台帳を消さず、原因を直してから再評価します。
