# 少額で始める分類

## 構成と設定

収集 (`npm run collect`) と有料の分類 (`npm run classify`) を分離しています。モデル設定がなくても文書の全件発見は続きます。未知の名称をキーワードで除外しません。

GitHub Actions Variables に設定:

| 名前 | 値 |
| --- | --- |
| CLASSIFIER_URL | OpenAI 互換 Chat Completions の HTTPS エンドポイント |
| CLASSIFIER_MODEL | 低価格の、JSON出力と max_tokens に対応するモデル名 |
| CLASSIFIER_INPUT_USD_PER_MILLION | 入力100万トークン当たりのUSD単価 |
| CLASSIFIER_OUTPUT_USD_PER_MILLION | 出力100万トークン当たりのUSD単価 |
| CLASSIFIER_MAX_USD | 累積予約額上限。未設定なら0.10 |

Actions Secret: `CLASSIFIER_API_KEY`。キーをチャット・Git・Variablesに入れないでください。例えば OpenAI を使う場合の URL は `https://api.openai.com/v1/chat/completions` です。モデルと単価は利用時の公式料金で指定します。単価が未設定なら有料処理を開始しません。クラウド環境から実行する場合はモデルのホストへのネットワーク許可も必要です。GitHub Actions の通信設定とは別です。

## 1. 少量評価

「Daily standards discovery」を手動実行し、mode=`evaluate` を選びます。ローカルでは `npm run evaluate`。

GNAP、OAuth、JWT、ACME、RATS、無関係なRFC、未知の用語を使った架空仕様、プロンプト注入を含む12件の人手作成の短い概要で評価します。公式本文の引用ではありません。期待ラベルはモデルに渡しません。

`reports/evaluation/latest.json` に再現率・適合率・判断困難数・実行時間・予約額・返却されたトークン使用量を保存します。モデル未設定時はテストデータの形式だけ検証し、精度は測定していないと表示します。

分類の開始条件は再現率90%以上、適合率80%以上、判断困難0件です。この12件は最低限の回帰チェックで、全48,000件の精度の保証ではありません。特に見落としと紛らわしい仕様を追加して評価セットを育てます。評価データ変更時は fixture version も更新してください。モデル・エンドポイント・プロンプト・評価セットの版が違う過去の合格結果は使えません。

## 2. 初回分類を再開可能な小分けで実行

評価結果を含む日次PRを確認・マージした後、同じワークフローで mode=`backfill`。通常は最大500件/実行（limit入力で変更、上限5,000）。10文書ずつ1リクエストにまとめ、予約額上限の方が先に尽きれば停止します。上限に収まるよう最後のバッチを小さくできます。

成功したバッチごとにカタログと進捗を保存します。途中のAPI障害でも完了分と費用予約をPRに残し、次の実行は未処理から再開します。日次PRブランチから未マージの結果も引き継ぎます。`reports/classification/` に完了文書、残件数、停止理由があります。

最初から全件完了を狙わず、初回結果の関連文書・除外文書を人が確認し、評価で得た文書当たり費用を参考に次の上限を決めます。精度に問題があればモデルや評価セットを修正します。既存の非関連判定を新モデルで再分類する機能はまだありません。

## 3. 日次処理

定期実行は mode=`daily`。全件発見の後、新規・更新文書を優先して最大30件を分類し、余力で既存の未処理文書を進めます。新規・更新日時を索引の追加要素として保持するので、後日の実行にも優先順位を引き継ぎます。判断困難の再試行には7日の間隔を設けます。

## 費用の扱い

`catalog/classification-budget.json` は評価と分類で共有する累積台帳です。上限は1日ごとのリセットではありません。0.10 USDを使い切ったら、明示的に上限を引き上げるまで有料処理を止めます。台帳を削除して残高をリセットしないでください。

送信JSONのUTF-8バイト数＋オーバーヘッドから入力トークン数を保守的に見積もり、出力上限と設定単価を合わせて**送信前に費用を予約**します。失敗・タイムアウトでも返金扱いにせず、モデルAPIを自動再試行しません。実使用量が少なくても予約は戻しません。小さい予算で予約が収まらない場合、有料呼び出しはゼロ件です。

この上限は設定単価・互換APIの出力上限が正しい前提のローカル予約額です。請求額そのものを保証する仕組みではありません。利用提供元の利用上限も併用してください。使用量を返さないAPIは予約額だけ記録し、実トークン数・実費を測定できたとは扱いません。

ワークフローは同時実行を禁止し、失敗時も台帳・完了分をPRへ保存します。PR保存が失敗した場合の復旧用にActions artifactにも保存します。PR保存やジョブが中断された場合は、再実行前にartifact/台帳の保存を確認してください。ローカルで分類コマンドを並列実行しないでください。
