# 有料APIを必須にしない候補抽出

既定のGHAはfastembedとBAAI/bge-small-en-v1.5をCPUで実行します。OpenAI等のキー・残高は不要です。公開リポジトリの標準GHAランナーを前提とし、GitHubの利用条件・実行時間・モデルダウンロードの制限は別途あります。モデルのライセンスはMITです。初回のバイナリはfastembedの対応する公式配布元から取得し、TLS検証を維持します。

## 使い方

「Daily standards discovery」のRun workflowで:

- `evaluate`: 74件の評価。26件がしきい値調整用、24件が初回試験からの回帰確認用、24件が新しい独立検証用。
- `backfill`: 初回データを分割処理。既定2,000件/実行。limitで件数変更。完了結果は64件ごとに保存し、次回は既処理フィンガープリントをスキップします。
- `daily`: 収集後、新規・更新を最大200件優先し、残りの枠で既存分を処理。

モデルと評価セットの変更時は再評価し、検証用データの再現率90%以上・適合率50%以上でなければ候補抽出を停止します。しきい値は調整用の正例・負例の境界からのみ決め、検証用ラベルを調整に使いません。評価失敗時はreports/semantic/evaluation.jsonを見て、対象範囲・例・モデルを見直します。74件の評価用概要は本PRで作成した回帰評価用で、専門家による独立ラベル付けは未実施です。これらは、公式概要の引用でも全件精度の保証でもありません。疑似文書も含みます。

## 保存と掲載

- catalog/reviewed.json: PRで人が確認する仕様。confirmedで掲載、excludedで候補を抑制。初期8件のRFCもこのPRの確認対象です。ドラフトの確認は指定版だけに有効。
- catalog/candidates.json: しきい値以上の関連候補。タイトル・版・時刻・スコア・理由だけ保持。人が確認したとは扱わない。
- catalog/semantic-index.json: 文書名→本文概要のハッシュ・スコア・版・時刻。本文とベクトルはGitに保存しない。
- reports/semantic/progress.json: 進捗、未処理件数 remainingCount と残件サンプル、低スコアから最大20件の再現可能な監査サンプル。

Pagesは確認済みと未確認候補を別表示します。低スコアは「無関係」にせず、索引に残して監査サンプルや後のモデル変更で再検討します。候補を確認したらreviewed.jsonに版と理由を記録しPRでレビューしてください。改訂されたドラフト候補は再計算まで掲載から外します。

## 制約と評価

モデルは入力を最大トークン長で切り詰めます。長い概要は後半が評価されないため、重要文書は本文を人が確認してください。埋め込みの意味距離だけで認証・認可との関係は保証できません。候補数、見落とし、監査サンプルを継続的に確認します。

初回は全件のメタデータをページングして未処理分を探します。未処理が2,000件以下なら、残ったIDを直接取得して補完し、一覧取得の取りこぼしを残しません。分割実行のたびに既処理のメタデータを再取得するので、APIの負荷・実行時間は計測して調整してください。新規・更新の優先処理も公式メタデータを取得します。モデルファイルだけをActions cacheに保存し、進捗はPRのデータから引き継ぎます。

ローカル検証:

```sh
python3 -m venv .venv-semantic
.venv-semantic/bin/pip install -r semantic/requirements.txt
.venv-semantic/bin/python semantic/pipeline.py --mode evaluate
python3 -m unittest discover -s semantic -p 'test_*.py'
```

有料モデル API の処理・設定・費用台帳は廃止しました。CPU 候補抽出だけを実行し、モデル API のキーは読み込みません。GHA への引数は mode と limit だけです。古い台帳や API 応答は Git 履歴で参照できます。

初回50件では独立検証の再現率83%（2件の見落とし）で停止しました。そのフィードバックを受けてクラス境界の方法に修正したため、元の検証24件は回帰確認用へ移し、別の24件を新たな独立検証用として追加しました。元の検証結果だけを使って改善精度を主張しません。

## レビュー作業を必須にしない運用

通常は候補一覧を閲覧するだけで構いません。候補を全部確認せず、実装したい仕様だけ原文・対象版・現在の状態を確認してください。機械の候補は未確認のまま掲載し、確認済みへ自動昇格させません。気になる誤検出だけreviewed.jsonにexcludedと理由を記録できます。

main上の収集ジョブが成功すると、生成データだけのPRを検査して通常のマージAPIで自動マージします。候補・進捗・収集索引・レポートなどの許可したJSONだけが対象です。コード、モデル/抽出設定、評価用データ、人の確認結果（reviewed.json）、ファイル削除・シンボリックリンクを含むPRは自動処理しません。失敗・処理中のレポートは自動処理せず、取得・抽出ジョブが失敗した場合も更新PRを残します。

マージ対象は同一リポジトリのgithub-actions botによるstandards/daily→mainのPRだけです。生成データの形式とPagesビルドを確認し、検査したSHAを指定してマージします。PR由来のコードは実行しません。ブランチ保護は回避せず、保護ルール等がマージを拒否した場合はPRを残します。

GitHubの予約型auto-merge設定や追加PATは不要です。GITHUB_TOKENでのマージはpushワークフローを起動しないため、Pagesをworkflow_dispatchで明示起動します。このため収集ワークフローにはactions:writeも付与しています。公開に失敗した場合はGitHub Pagesをmainで手動実行できます。コードや抽出ルールのPRは引き続き人がレビューします。
